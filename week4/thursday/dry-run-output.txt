per-host into the loop, Deploy systemd unit file) before the run hits "Enable service".

Known --check-mode limitation (not a real failure):
  The "Enable service" task fails under --check with "Could not find the requested
  service kk-<name>.service: host". This happens because ansible.builtin.systemd does
  not support check mode for querying/managing a real unit - in --check, the preceding
  "Deploy systemd unit file" template task is only *simulated* (reported as would-be
  changed) and never actually writes /etc/systemd/system/kk-<name>.service to disk. So
  when "Enable service" tries to query systemd about a unit that doesn't really exist
  yet in this check-mode run, it correctly reports "Could not find the requested
  service". This is documented Ansible behavior: most service/systemd modules cannot
  be meaningfully dry-run when the unit they manage is created earlier in the same
  play. It is not evidence of a bug in the playbook.
  Confirmed by running the real (non-check) apply immediately after: Phase 4's
  apply-run1.txt shows the same unit files being created and then successfully
  enabled/started with no errors, proving the --check failure was purely a tooling
  limitation and not a defect that needed fixing before applying.
